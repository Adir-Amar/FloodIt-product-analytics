# Notes Ledger — Flood-It Product Analytics (raw session notes, README source material)

Day 1: Setup done. Starred the public dataset firebase-public-project.analytics_153293282: 114 daily event tables (consecutive days) from the mobile game Flood-It. Scale: 5.7M events (suspiciously round — data likely trimmed for the demo) across 15,175 distinct user_pseudo_ids. Caveat: pseudo ID = one per app install/device, not per person, so unique human players ≤ 15,175.

Day 2: Event census done (37 event types). Key findings: (1) Deliberate monetization is extremely rare — 27 purchase events by 27 distinct users (no repeat buyers) and 1,912 rewarded-ad views across 354 users in 114 days; note ad_reward covers only opt-in rewarded ads, not banners/interstitials. (2) Only 4,322 users have first_open in-window → the other ~10.8k installed before the window (left-censored) and are a survivor-biased sample; D1/D7/D30 retention must therefore be computed only on the ~4.3k in-window installers. (3) Hypothesis, unconfirmed: two game modes (campaign level_start vs dominant quickplay ~7:1). (4) post_score (242k events / 8.6k users, ~28 per user) is far too high-volume to be a deliberate social-share action — almost certainly an automatic score submission. Verify via params. (LinkedIn material: post_score hypothesis killed by a volume sanity-check — good story about verifying event definitions before theorizing.)

Day 3: Cracked event_params via UNNEST. Findings: (1) params are not guaranteed per event — always count, never assume (e.g. time present on only 60% of post_score). (2) score is logged as int on some events, double on others (likely platform split) — rule: always COALESCE(int_value, double_value) or risk silently dropping a type's worth of data. (3) firebase_* params are SDK housekeeping, not game data. (4) score is a bounded integer 0–21, mass decaying from 0, anomalous spike at the ceiling (21) — open anomaly, unexplained. (5) Verdict: post_score = automatic score submission around level completion (volume ≈ completions, every event carries level+score); social-share theory conclusively dead. Exact trigger unresolved and deliberately not pursued.

Day 4 — Retention metric definitions (locked): Calendar-day convention via event_date (GA4 standard). Day 0 = user's earliest first_open date (MIN per user — 3 users have duplicate first_opens; cohort = 4,319 distinct users, not 4,322). Retained-on-N = ≥1 event of any type on exactly day 0 + N (caveat: includes app_remove etc., accepted noise). Eligibility anchored to dates: day 0 ≤ 2018-10-03 minus N days. Retention rate = eligible-and-retained / eligible, per N. (Meta-lesson logged: unpinned indexing conventions produced a fake disagreement between me and Claude — pin conventions in writing, always.)

Day 5: Built classic D-N retention (flags-CTE + conditional-aggregation architecture). Results with proper per-N denominators: D1 21.52% (4,251), D3 10.48% (4,151), D7 5.58% (3,998), D14 3.69% (3,711), D30 2.09% (2,963) — clean decay curve, slightly below casual-mobile benchmarks. Calibration lesson: initial gut prediction (90/55/35) was off by ~70pp — reference-class error, priors imported from high-investment genres (console/gacha) onto frictionless casual F2P. Communication rule locked: percentage points vs relative %, relative change always over baseline. Rule logged: filters that hide unexplained rows are evidence destruction, not cleaning.

Day 6: Contamination audit closed: 12 distinct players (0.28% of 4,319) have activity before their computed day 0 — pre-window installers who reinstalled in-window (~11 pre-window active days each). Decision: below materiality (max effect ~0.3pp < rounding); retention results stand unmodified; documented as known caveat. Lesson: quantify-then-decide beats rework-by-reflex.

Day 7: GitHub repo created (private) — sql/ (event_census, retention_curve), notes/ (this ledger), data/, notebooks/. Pulled day_0 (4,319 × 2) and user_journal (59,037 × 2) from BigQuery into Colab via the BigQuery Python client; journal row count verified independently on both platforms (59,037 = 59,037 — cross-platform reconciliation habit). Dtypes checked: client preserved real date types (dbdate), so date math works in-notebook. Known trap ahead: the tables were saved to CSV (text format, no types) — on reload, dates come back as strings unless explicitly parsed; handle at load time next session. Derived fact: 59,037 / 15,175 ≈ 3.9 active days per user on average. Notebook saved to repo as notebooks/01_retention_pandas.ipynb.

Day 8: Rebuilt the retention pipeline in pandas (02_retention_analysis.ipynb). CSV reload: dates came back as strings exactly as predicted last session — fixed at the boundary with parse_dates= on read. Architecture mirrors the SQL CTE chain: inner merge (day_0 × journal, 11,346 rows) → days_between via datetime subtraction → per-player flags via groupby().agg('any') (LOGICAL_OR cognate; sum rejected — right numbers, wrong meaning) → eligibility cutoffs + rates. Result: all 15 numbers (eligible/retained/rate × 5 Ns) match SQL digit-for-digit — retention curve now cross-validated by two independent implementations. Contamination reconciled independently: 130 pre-day-0 rows / 12 distinct players (pre-window installers who reinstalled in-window), matching the Day 6 audit; below-materiality decision stands. Prediction miss logged: estimated merge rows via the full-population average (3.9 active days/user) → 16.8k vs actual 11.3k (~48% overshoot). Lesson: population average ≠ subgroup average — the cohort runs ≈2.6 days, pre-window survivors ≈4.4; ask "does my average come from this group?" before borrowing it. Derived split is a real finding for later activity EDA.

Day 9: Retention curve visualized twice, by audience: linear plot (stakeholders — honest axes, y from 0) and log-log (analyst diagnostic — a power law y = A·N^k is a straight line in log-log, so straightness tests whether one decay law summarizes the curve). Segment slopes: [-0.65, -0.74, -0.60, -0.75] — alternating around ≈ -0.7 with no monotone trend (trend would mean regime change; alternation suggests noise). Noise check via standard errors: D14 SE ±0.31pp, D30 SE ±0.26pp; both tail deviations from the D1-anchored trend (21.52 × N^-0.69) fall within ±2SE → bends consistent with sampling noise. Verdict: five points consistent with a single power law, exponent ≈ -0.7. Licenses in-window interpolation and cautious, labeled extrapolation (D60/D90) — estimation, not determination: exponent is a mean of segment slopes (not a fit), five points, and regime change beyond the window can't be excluded.

Day 10: Activity-patterns EDA opened (notebook 02). Per-user active-day counts built from the journal (groupby-count, 15,175 users), tagged cohort vs pre-window via isin. One-day-only players: 54.2% of cohort (2,341/4,319), 50.8% of pre-window (5,515/10,856). Prediction miss logged: predicted 78.5% off the D1 retention rate — but "not D1-retained" ≠ "one active day": retention is exact-day-N, so users can miss day 1 and return later. The gap is the finding: ~24pp of the cohort (≈31% of D1-missers) skip day 1 but come back eventually — D1 retention alone undercounts salvageable players. Distribution shape: median 1 active day in both groups, 75th pct = 3, heavy right tail (std ≈ 2× mean; top user active 114/114 days of the window). Histogram (shared bins range(1,116), density-normalized, log-y): the two groups' shapes coincide at the head, where ~90% of players live and both are fully observable; orange (pre-window) dominance in the deep tail is largely manufactured by censoring (114 in-window days requires pre-window install; cohort survival to 80+ days is priced at ~single players by the retention curve) — verdict: consistent with one population seen through two observation windows; "more dedicated pre-window players" can't be separated from selection effect. Censoring asymmetry pinned: pre-window counts = in-window activity only (lifetime undercount); cohort = lifetime but right-truncated. Pandas gotcha logged: integer bins= slices each series' own range → unequal bin widths across groups; explicit shared edges (bins=range(...)) are the fix for multi-group histograms. Meta: histogram spec was deviated from silently (integer bins for the given edges) — rule reaffirmed: deviate from a spec openly or not at all.

Day 11: Weekday rhythm + DAU investigation (notebook 02). Weekday bar chart (fair unit: avg active users per day-instance; occurrence counts via nunique on dates — Tue/Wed carry 17 instances, rest 16) initially showed Mon/Tue peak, Wed/Fri trough; weekend-vs-weekday gap only +1.4% vs predicted +10–15%. DAU time series exposed the cause: seven spike days (Jun 18: 1283, Jun 19: 1240, Jun 25: 1235, Jun 26: 1187, Jun 28: 1219, Jun 30: 1211, Jul 1: 1225) — ~2.5–3× the ~470 baseline, interleaved with normal days, then never again (Sep 27's 644 is mild wobble, kept in-window). Earlier claim "spikes are all Mon/Tue" — falsified by the full listing (Mon/Tue/Thu/Sat/Sun); lesson: head/tail sampling produced a universal claim from 25% of data — list before generalizing. Stable window pinned by date (Jul 2 onward, 94 days; date cut = regime claim, value cut = selecting on the outcome — rejected). Stable-window verdicts via SE = std/√n (daily std 50.6, weekday SE ≈ 14, pairwise threshold ≈ 40; pooled threshold ≈ 23): max weekday gap 30.7 < 40; weekend gap 13.1 (470.8 vs 483.9) < 23 — the entire weekly rhythm is noise; the "pattern" was the June fortnight in costume. Sanity-catch logged: first pooled attempt averaged the averages → 34.6, below the window's worst day (346) — impossible on sight; read outputs for plausibility before reporting. Spike anatomy: install logging flatlines on spike days (Jun 18/25/28/30, Jul 1: zero first_opens; Jun 19: 10; Jun 26: 1; baseline ~38/day) while spike-day user-days are 97.2% pre-window players vs 78.0% on normal days. Predictions: weekday-collapse — hit; install-spike — inverted (installs cratered, not spiked); pre-window share — direction hit, magnitude undershot (guessed 65–70%) by treating full cohort attendance as the scenario instead of pricing attendance with our own retention curve — second magnitude-miss from not applying a curve we own. Hypotheses, labeled, undecided (needs event-level pull): (a) re-engagement push to installed base — doesn't explain zero installs; (b) in-game/seasonal event — same gap; (c) data artifact (first_open logging gap or demo-dataset trimming — recall Day 1's "suspiciously round 5.7M, likely trimmed") — only story that naturally produces an install blackout.
